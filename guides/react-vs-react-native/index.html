React vs React Native: which should you use?

React JS vs React Native is a runtime, UX, distribution and maintenance decision. In our experience, most existing products should begin with the web application they already have.

React JS and React Native solve different problems

React renders web interfaces in a browser. React Native renders platform UI and gives direct access to native modules. A shared language does not make their components interchangeable.

Our default: web plus Capacitor

For most products we have worked with, a responsive web app packaged with Capacitor is enough. The path from a working web product to iOS and Android builds is fast, the web remains the source of truth, and ongoing maintenance stays inexpensive because web, iOS and Android share one source codebase.

Capacitor provides a native runtime, lifecycle and plugin bridge around the web application. The result can behave like an installed app while the product team continues shipping the same core code.

Native capabilities do not require a rewrite

Camera access, push notifications, deep links, secure storage, biometrics, files, geolocation, haptics and in-app purchases can be added through existing Capacitor plugins. When an SDK or platform capability has no suitable plugin, a focused custom plugin can expose Swift or Kotlin code to the web application.

Some native functionality can live in a small app-specific layer while the product stays on the shared web codebase.

When React Native or fully native wins

Choose Expo or React Native when native navigation, complex gestures, background execution or sustained UI performance are central to the product. Choose Swift and Kotlin when the product depends on platform-specific frameworks or exceptional interaction quality.

Wrapper / CapacitorBest when the web UX already works on mobile and native needs are limited.
Expo / React NativeBest when mobile navigation, device APIs and app-like performance matter.
Native iOS + AndroidBest for deep platform integration, but highest build and maintenance cost.

Decide with a release spike

Prototype the hardest mobile requirement first: authentication handoff, purchases, notifications, deep links, background work or offline behavior. Let that result choose the architecture before rebuilding the whole product.
